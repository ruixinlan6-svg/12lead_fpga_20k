# 优化迭代记录规范

## 目的

让任何人都能回答：某个模型、量化包、RTL、比特流或板测结果是怎样产生的，为什么采用该优化，以及它相对哪一轮发生了什么变化。

## 一轮实验的定义

以下任一变化都必须创建新的迭代记录：

- 数据版本、患者划分、预处理或增强变化；
- 模型结构、损失函数、训练超参数或随机种子变化；
- PTQ/QAT 校准集、位宽、scale、zero-point、舍入或饱和规则变化；
- GoAI 模型转换、算子替换、张量布局或厂商配置变化；
- RTL 算子、SIMD、缓存、DMA、时钟或协议变化；
- 综合选项、时序约束、引脚、下载方式或板测条件变化。

失败、无收益和人为中止也属于一轮实验。

## Run ID 与文件位置

格式：`YYYYMMDD-HHMM-<stage>-<short-name>`。

阶段名使用：`data`、`train`、`quant`、`goai`、`rtl`、`synth`、`hil`、`external`。

记录文件放在 `docs/iterations/records/<run_id>.md`，并在 [INDEX.md](INDEX.md) 增加一行。旧文件只允许补充缺失的客观结果和链接，不得修改原始假设、优化原因或验收标准；若要改变这些内容，创建新 `run_id`。

## 执行前必须填写

- `run_id`、阶段、责任 Agent、时间和父级 `baseline_run`；
- Git commit、数据版本/split 哈希、配置路径和模型/硬件契约版本；
- 当前问题与证据；
- 本轮优化手法；
- 为什么选择它，以及没有选择哪些替代方案；
- 预先冻结的成功/失败门槛。

禁止先看测试结果再补写优化原因或降低门槛。

## 执行后必须填写

- 实际命令或入口脚本、环境、GPU/EDA/器件版本；
- 优化前、优化后和差值；
- 训练指标、量化指标、逐层误差、资源、Fmax、延迟和功耗中适用于该阶段的项目；
- 失败样本、异常日志和未验证项；
- 产物路径及 SHA-256；
- 最终决定：`accept`、`reject`、`rollback`、`continue`；
- 下一轮只允许解决的一个主要问题。

## 指标比较规则

- 必须与明确的 `baseline_run` 比较，不能只报告本轮绝对值。
- 数据、split、阈值或测试条件不同，必须标记为“不可直接横向比较”。
- 推理核心延迟与包含 UART/文件 I/O 的端到端延迟分开报告。
- 综合估算功耗与实测板级功耗分开报告。
- 软件整数参考与 RTL/板端的数值一致性优先报告首个失配点，不用最终分类正确掩盖中间错误。

## Git 提交门禁

包含训练、量化、GoAI、RTL、综合或板测结果的提交，必须同时包含对应记录和索引更新。模型、数据、比特流或日志过大时不提交文件本体，但必须记录保存位置、哈希和生成它们的 commit。
