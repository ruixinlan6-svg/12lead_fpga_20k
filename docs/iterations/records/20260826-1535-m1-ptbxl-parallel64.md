## Problem and evidence

- The 16-worker downloader was correct but too slow for the full `records100` tree.
- Partial files already present in the remote private directory are retained and will be reused by SHA-256 after the transfer completes.

## Optimization

- Method: bounded 64-worker parallel download, still using atomic `.part` files and no deletion.
- Why this method: test whether the bottleneck is connection concurrency while keeping dataset bytes and provenance unchanged.
- Alternatives considered: changing sampling rate, downloading unrelated caches, or writing data into the public repository. Rejected for contract/provenance reasons.

## Frozen acceptance criteria

- PTB-XL 1.0.3, `records100/*_lr.{hea,dat}` only.
- Metadata hashes and registry counts remain unchanged from the validated metadata run.
- No raw data, checkpoint, or remote credentials enter Git.

## Execution

- Remote root: private `LRX/12lead_fpga_20k_m1/data/ptb-xl/1.0.3`.
- Worker count: 64.

## Results

- The remote process was stopped after repeated `WinError 10060` timeouts from PhysioNet. No checksum mismatch was observed; existing complete files remain reusable and partial `.part` files were cleaned by the downloader.
- Full per-file acquisition is not an efficient prerequisite for the first software smoke test under this network path.

## Decision

- Do not keep the 64-worker full-tree attempt running. Create a new bounded-sample run for the first training/quantization vectors; revisit full-tree acquisition only with a bulk archive or a better mirror.
